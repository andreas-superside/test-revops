Build in Team. Share from Enterprise.

One process for moving an artifact from a department Team workspace to the Enterprise workspace, so the whole company opens the same link. Heavy building stays on Team. Day-to-day use happens on Enterprise. The first pilot ran end to end. This page covers the process, what the pilot proved, and what we still need to test.

Part 1

Artifact sharing

Building and sharing, step by step

The owner runs four steps. GitHub carries the file between the two workspaces, because the workspaces cannot talk to each other directly.

  1. 1
    Team workspace

    Build the artifact

    Create and iterate in your department's Team workspace. Experiments and heavy usage stay on the Team plan.

  2. 2
    Team workspace to GitHub

    Publish to Enterprise

    Run the release skill. It saves artifact.html, spec.md and release.json to your GitHub repo and gives you a one-line prompt to paste into Enterprise. The saved artifact.html is always the clean version.

  3. 3
    Enterprise workspace

    Release in Enterprise

    Paste the prompt. Claude reads the folder from GitHub, publishes the file unchanged, and you choose who can open it. The new link is saved to release.json in the same folder.

  4. 4
    Team workspace

    Finish the release

    Run the finish step. The Team copy is republished with a banner: "Dev copy. Use this link instead", pointing to the Enterprise artifact. The banner is added only when the Team copy is published and is never saved to GitHub.

Updating after release

Changes move in one direction only: GitHub, then Team, then GitHub, then Enterprise. Nobody edits the Enterprise copy.

You changed the artifact

Release again from Team

Change it in Team, run the same steps, and the Enterprise artifact updates in place. The link stays the same.

Enterprise looks out of date

Refresh from GitHub

In Enterprise, tell Claude to refresh the artifact from GitHub. It republishes whatever version is committed.

  • Share the Enterprise link only.The Team link is the dev copy and may not open for everyone.
  • GitHub holds the source.The file that gets released is the file in the repo, never a rebuild from a prompt.

What every team needs to start

Two requirements.

Requirement 1

The release skill, mandatory

One skill that describes and runs this whole process. It is installed in both the Team and the Enterprise workspaces, and everyone uses it.

Requirement 2

A GitHub account for everyone

A company-owned account in the company organization, connected in both workspaces. Work then survives when a user is deactivated.

What the pilot showed

A throwaway artifact went through the full flow, including an update, using Claude Code sessions on a Team login and an Enterprise login with one private GitHub repo.

  • WorkedTeam to GitHub. The artifact was published and its three files were pushed to the repo.
  • WorkedGitHub to Enterprise. The Enterprise session published the file unchanged and wrote its link back to release.json.
  • WorkedThe banner. The Team copy read the Enterprise link from release.json and showed the "Dev copy" banner.
  • WorkedUpdates. A new version released from GitHub kept the same Enterprise link, and the Enterprise page showed no banner.
  • ChangedThe banner is never committed. The first run saved the banner into artifact.html, so the next Enterprise refresh would have carried it over. The repo file stays clean and the banner exists only on the Team copy.
  • ChangedThe commit step used Claude Code. Pushing to a private repo needs the Claude GitHub App installed on that repo. Building still happens wherever people build today.
  • CheckedNo GitHub Pro needed. Pro is for personal accounts. A free organization allows unlimited private repos. A paid organization plan is needed only for enforced reviews such as protected branches and required reviewers.

Still to test before rollout

  • Who can open what. Whether a Team link opens for a user who is only in Enterprise, and whether Enterprise can be set to open for the whole organization.
  • Company ownership. The pilot repo sits under a personal namespace. Repeat it with company-owned accounts and repos in the company organization, with the Claude GitHub App installed by an organization admin.
  • Teams without Claude Code. Whether a regular chat can commit to GitHub, or needs a connector with write access. The fallbacks are a Claude Code session for the commit, or uploading the files in GitHub by hand.
  • One-click release. Whether a button in the Team artifact can open a prefilled chat that starts the release or refresh.
  • A second department. A team outside RevOps runs the process end to end using the release skill.
Part 2

Skill sharing

In the works

Skills will follow the same principle as artifacts, with GitHub as the source. The release route for skills is being defined.

Open questions

  • Distribution. Whether a plugin can be installed organization-wide in both workspaces, and whether an update reaches both automatically.
  • Review. Skills change how Claude behaves for everyone who uses them, so they likely need review before release. Enforcing that on GitHub needs a paid organization plan.
